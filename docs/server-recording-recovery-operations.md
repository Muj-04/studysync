# Recording operations rollout and recovery

This change is not deployed. The worker is a one-shot executable, with no scheduled job or hosted configuration created by this branch.

## Coordinated cutover

1. Back up database metadata and audio objects independently. Inspect the deployed catalog: both `voice_notes.id` and `room_voice_notes.id` must be UUID, and both `page_number` columns must be TEXT/VARCHAR. The migration preflight rejects incompatible columns before making changes; it does not normalize IDs, foreign keys, or integer page columns. No authoritative hosted base-schema snapshot was available locally, so catalog compatibility remains a release gate rather than an established fact. Review `recording_private.untracked_audio_inventory` after migration and inventory pre-existing Storage objects without metadata before release; this privileged read-only view lists unadopted paths and does not authorize cleanup. Review duplicate note UUIDs across personal/room tables and legacy audio paths before applying migrations; migration failure rolls back atomically.
2. Require the documented `storage.allow_only_operation(text)` helper in the deployed Storage schema (missing support fails migration closed). Only standard `object.upload` is permitted; signed-upload token issuance, copies, S3 and resumable alternatives are denied for client writes. Require bucket versioning `DISABLED` and no archived versions/delete markers; the migration rejects other configurations and cleanup rechecks the bucket mode. Keep versioning disabled while this protocol is active. Verify the `voice-notes` bucket is private through the Storage API; the migration rejects a missing/public bucket because public URLs bypass RLS. Apply the document-generation migration, then `20261028203014_server_recording_operations.sql` in a planned maintenance window. This is an intentional protocol cutover: restrictive Storage policies and metadata guards reject old direct recording uploads/publications. Old open tabs must reload. There is no silent fallback after cutover.
3. Deploy the client built with `NEXT_PUBLIC_SERVER_RECORDING_RECOVERY=true` and the `/api/recordings/[operationId]/audio` endpoint. Configure `SUPABASE_SERVICE_ROLE_KEY` only in the server runtime; never expose it through a public environment variable. Keep the flag false only before migration, when the legacy browser journal is still the active protocol.
4. Operate the worker using server-only `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY`, with Node 22+ and installed repository dependencies:

   ```sh
   node scripts/run-recording-worker.cjs --run --limit=20
   ```

   Each invocation handles at most 20 attempts over at most one minute, with request deadlines. An operator or separately approved scheduler must invoke later passes. No scheduler is installed here. Monitor queue age, `attempts`, `last_error`, expired leases and `blocked` rows through a privileged database connection. Repeated failures back off up to five minutes, rather than recursively retrying within the browser. Lease expiry is two minutes.

5. Validate compatibility of the narrow `storage.objects` commit trigger with the deployed Storage version, including its permission probe and final admin insert. The trigger function lives in `recording_private`; it rejects stale final inserts and immutable-object changes even when Storage bypasses RLS. Supabase discourages managed-schema alterations, so this explicit compatibility check is a release gate, and upgrades must repeat it. Validate actual hosted Storage upload metadata, immutable insert policies, signing, removal acknowledgments and the browser playback redirect before release. Local SQL tests simulate Storage object metadata; they do not prove physical provider behavior. A successful physical DELETE must also remove its Storage metadata before the worker can mark cleanup complete.

## Recovery policies

Operation IDs and note IDs are permanent. The original owner, scope, generation, object path and payload size/type cannot change. Uploaded bytes can publish after a browser disappears; revoked unpublished work or expired intents with no committed object move to cleanup. Valid committed bytes remain eligible for bounded publication retries regardless of the upload deadline. A cancelled/deleted operation cannot be reused even if a stale tab still has its Blob. Saving that audio again requires an explicit new recording copy and current parent generation.

The one-hour deadline closes admission of new uploads; it does not expire audio already committed to Storage. A worker outage or metadata-write failure can be retried after that deadline while ownership and scope remain valid. Size/type mismatches are quarantined as `blocked` with their bytes retained, not automatically removed; they require explicit owner deletion or operator reconciliation. Audio that never reached Storage cannot be reconstructed by the worker. Keep/export local audio through the owner-scoped recovery UI before closing a failed-save tab; browser-local retention remains subject to browser storage availability and deletion. Do not interpret a server operation record as proof that the Blob was uploaded. The adapter never discards its caller's Blob on errors.

Existing metadata is adopted in the migration. Conventional paths are accepted only when the owner, document/room and note IDs match exactly; unknown paths remain `blocked`, preserving the existing playback URL. While any referenced legacy row remains blocked, cleanup of all adopted legacy objects is conservatively paused: unknown URLs may alias otherwise verifiable paths. New operation paths are unaffected. An operator must reconcile ambiguous paths and all references before cleanup; the worker never guesses object paths. Legacy signed URLs retain their previous expiration/revocation properties until separately migrated. Legacy browser journal entries whose uploads never published cannot be reconstructed from metadata alone: export retained local audio and inventory orphan objects separately. No bucket-wide orphan deletion is attempted.

The playback endpoint rechecks authorization before issuing a new URL. A previously issued signed playback URL can remain usable until its requested 60-second expiry and any provider cache behavior; this does not provide instantaneous revocation of an already-issued URL. Hosted acceptance must verify expiry/cache behavior.

Published room contributions remain shared after their author leaves. Revoked members cannot delete published room contributions through the new RPC; unpublished operations can still be cancelled safely. Parent document cascade deletion durably queues published audio cleanup; pending publication rechecks the deleted generation. Privileged manual database or Storage edits can violate application invariants and are outside these guarantees.

## Local verification

`node --test tests/server-recording-*.test.cjs` exercises SQL roles/RLS, immutable paths, generation/room/account revocation, leases, publication/deletion, legacy references, client ordering and worker failures. These use PGlite and controlled client doubles.

`scripts/test-recording-postgres.cjs` additionally requires a disposable PostgreSQL database named `integrity_recordings`, a local Unix socket, and the generation migration. It drops schemas in that database. Configure `RECORDING_TEST_PG_SOCKET`, `RECORDING_TEST_PG_DATABASE=integrity_recordings`, optionally `RECORDING_TEST_PSQL`, `RECORDING_TEST_PG_PORT`, `RECORDING_TEST_PG_USER`, and `RECORDING_TEST_GENERATION_MIGRATION`, then invoke with Node. It exercises independent connections for exclusive claims, deletion before a delayed begin, and publication versus document deletion, followed by cascade cleanup and tombstone rejection. It cannot contact hosted PostgreSQL because an absolute Unix socket is required.

Policy operation names follow [Supabase Storage helpers](https://supabase.com/docs/guides/storage/schema/helper-functions) and the [official operation list](https://github.com/supabase/storage/blob/dd17e18aa3fed0e6f869a8c337f0713e473f98a4/src/http/routes/operations.ts). Physical object operations always use the Storage API, as required by the [Storage schema documentation](https://supabase.com/docs/guides/storage/schema/design).

The final commit fence addresses the official [Storage uploader](https://github.com/supabase/storage/blob/dd17e18aa3fed0e6f869a8c337f0713e473f98a4/src/storage/uploader.ts) path that probes caller permissions before an admin write; [permission testing](https://github.com/supabase/storage/blob/dd17e18aa3fed0e6f869a8c337f0713e473f98a4/src/storage/database/pg.ts) rolls back its probe transaction. Local tests reproduce that boundary. Provider cleanup of bytes after a rejected final metadata insert must be verified in hosted acceptance; rejected bytes are not represented by a committed object row, so an application worker cannot inventory the underlying provider directly.

The supported Storage cleanup mode is nonversioned (`DISABLED`, including older schemas without that field). The official database adapter performs `DELETE FROM storage.objects` in that mode; versioned modes create delete markers and preserve older bytes, so this implementation rejects them rather than relaxing object immutability or claiming physical deletion. Local cleanup tests model the nonversioned database path. Hosted acceptance must record the deployed Storage version/commit and verify this behavior; no deployed provider version has been verified here.
